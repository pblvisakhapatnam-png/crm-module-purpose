# Documents Contract

## Purpose

This contract defines the early document metadata foundation.

The first prototype does not require SharePoint integration. It must, however, preserve document metadata and linkage so that SharePoint or another repository can be added later.

## Initial document handling

Slice 0 should create the foundation.

Slice 1 may use document metadata for Account-linked documents.

Supported initial storage modes:

```text
local_upload
external_link
future_sharepoint
```

## Minimum metadata

```text
document_public_id
document_type
linked_record_type
linked_record_public_id
file_name
original_file_name
storage_mode
storage_path_or_url
version_no
status
uploaded_by
uploaded_at
remarks
```

## Document status examples

```text
Draft
Uploaded
Linked
Verified
Rejected
Archived
```

## Business rules

- A document must be linked to a business record or clearly marked as unlinked/staged.
- Document metadata must not depend on a specific storage provider.
- Later document locking/versioning must be possible.
- Do not silently overwrite submitted or verified documents in later modules.

## Out of scope for initial slice

- SharePoint sync.
- OCR or AI extraction.
- legal hold/retention automation.
- advanced access groups.

## Slice 9C - Document Storage Foundation

Slice 9C implements the storage abstraction this contract's Purpose section promised - a real
local storage provider behind an interface, so a later SharePoint provider is a swap plus a file
migration rather than a rewrite - and closes two defects verified against the pre-9C code:
`storage_mode = 'local_upload'` was accepted although no file upload existed anywhere in the
backend, and all four pre-existing `/api/documents/*` routes were authenticated-only with no
role or record-scoped distinction at all. See
`docs/agent/slices/slice-9c-document-storage-foundation.md` for the full design record,
including the five business decisions the project owner made before this slice was designed.

### Backend routes

```text
GET  /api/documents/types
GET  /api/documents/recent
GET  /api/documents/by-record/{record_type}/{record_public_id}
POST /api/documents/metadata
POST /api/documents/upload                     new
GET  /api/documents/{public_id}/content         new
```

### Storage abstraction

```text
backend/app/modules/documents/storage/
    base.py    DocumentStorageProvider ABC, StoredObject, provider exceptions
    local.py   LocalFilesystemStorageProvider (the only provider today)
```

`storage_key` is opaque and generated by the service layer, never by the caller and never
derived from a caller-supplied file name. No filesystem concept crosses the provider interface.
Configured by `DOCUMENT_STORAGE_ROOT` (default `/app/document-store`), backed by a named Docker
volume so files survive restarts and image rebuilds.

### New `document_metadata` columns (Alembic `20260908_0034`)

```text
storage_provider_code   which provider holds the bytes (e.g. "local")
storage_key             opaque provider key - never exposed outside the storage module
content_type            declared/validated MIME type
byte_size               actual byte count, counted while streaming
checksum_sha256         integrity evidence
retention_due_at        SHAPE ONLY - never set by this slice; see Deferred below
```

`ck_document_metadata_local_upload_has_bytes` is a database CHECK constraint: a row cannot claim
`storage_mode = 'local_upload'` unless `storage_provider_code`, `storage_key`, `byte_size` and
`checksum_sha256` are all populated. This holds even against a direct `INSERT` that bypasses the
API entirely - `local_upload` is reachable only through `POST /api/documents/upload`, which is
the only code path that actually stores bytes. `POST /api/documents/metadata` rejects
`storage_mode = 'local_upload'` at the API layer as a first line of defense; the CHECK
constraint is what holds if that check is ever bypassed.

### Upload limits (owner decision, 8 September 2026)

Up to 25 MB (`MAX_UPLOAD_BYTES`); PDF, Word, Excel, common images, plain text and CSV
(`ALLOWED_UPLOAD_EXTENSIONS`), validated on both the file extension and the declared content
type. Size is enforced by counting bytes as they are actually read from the upload stream,
never by trusting a caller-declared `Content-Length` header or form field.

**Added September 2026, after independent review of the upload package (round 1).** An extension
and a declared content type are both only the caller's claim, so two further limits apply:

- **Each request is capped as it arrives.** FastAPI reads a request's whole form or JSON body before
  it runs any dependency, authentication included, so an upload of any size, from any caller, was
  received and spooled to a temporary file before it could be refused. Every documents route now
  uses a route class (`_BoundedBodyRoute` in `routes.py`) that counts the body's bytes as they
  arrive and answers `413` once they pass `MAX_DOCUMENTS_REQUEST_BYTES` - 25 MB plus 1 MB for the
  form's other fields. Like the storage limit, it counts bytes and consults no declared size. It
  runs before the body is parsed and before authentication, so the most any caller can make the
  server receive is one bounded request.
- **A file's content must match its extension.** Before a byte is stored, the file is checked
  against its format (tightened in round 2): a `.pdf` must start with `%PDF-`, and a `.png` or `.jpg`
  with the PNG or JPEG signature. A `.doc` or `.xls` must be an Office 97-2003 compound file with a
  `WordDocument` stream, or a `Workbook` or `Book` stream, at the top of its directory tree, so a
  PowerPoint deck, an Outlook message or a Windows installer, which are compound files too, is
  refused under either name. The tree is walked from the root entry through its child and sibling
  links, so a name no link reaches, or one inside a sub-storage, does not count (round 3). Only the
  compound file's header, allocation table and directory are read, with every sector index checked
  against the file's length, every entry ID against the directory's size, and every chain and the
  tree walk guarded against loops. The header's allocation-table counts must match what it lists,
  with no table sector listed twice and no more of them than the file's size needs, and table
  entries are read only as the directory chain needs them; every reached entry's name must be well
  formed - an even length, a closing NUL, strict UTF-16 and no other NUL (round 4). A `.docx` or
  `.xlsx` must
  be a ZIP archive whose directory lists `[Content_Types].xml` and `word/document.xml` or
  `xl/workbook.xml`, and no `vbaProject.bin` part, so a macro-enabled `.docm` or `.xlsm` renamed is
  refused. Before that directory is read, the archive's end record must describe one disk, no ZIP64
  extension, at most 10,000 entries and a directory of at most 1 MB (round 5); the directory's own
  entries are then counted over those bounded bytes and cross-checked against the end record's
  claim, because the count in the end record is only a claim (round 6); and the directory must end
  exactly where the end record begins, so an archive with data prepended before it - whose stored
  offset would point away from the directory the reader actually opens - is refused (round 7). A `.doc` or `.xls`
  allocation-table (DIFAT) chain is bounded the same way: the header's list-sector count must equal
  exactly what the table needs, and no list sector may be read twice (round 6). `.txt` and `.csv` must be text: no NUL byte in the first 8 KB, unless a UTF-16 byte-order
  mark announces UTF-16 text. A mismatch is `422`, and so is any failure while reading a compound
  file's or a ZIP archive's structure - never a server error. These are format checks, not a malware
  scan, and text is not interpreted.

  **What the check does not do.** It confirms how a file is built - a PDF header, an image
  signature, an Office compound file holding the Word or Excel stream, an Office Open XML package
  holding the Word or Excel main part - not that the document inside is complete, valid or
  uncorrupted. A damaged or hand-assembled file built that way is accepted. This is a deliberate
  limit, decided by the project owner on 11 September 2026 after review round 5.

### Authorization

Three new permission codes (`DOCUMENT_READ`, `DOCUMENT_UPLOAD`, `DOCUMENT_CONTENT_READ`),
added to `POST_BASELINE_ROLE_PERMISSION_MATRIX` in
`backend/app/modules/authorization/contract.py`. All three are currently granted to all six
roles, reproducing the pre-9C authenticated-only reach of these routes exactly at the route
level - **the real narrowing this slice adds is a second, record-scoped, fail-closed check in
`documents/service.py`**, not a role restriction: a caller may see or download a document only
if they may independently read the record it is linked to
(`DOCUMENT_LINK_READ_PERMISSION` in `documents/contract.py`), and downloading a document linked
to a customer conversation additionally requires `INTERACTION_CONTENT_READ` (Slice 9D), so an
attachment cannot be used as a pointer around that slice's content redaction. An unmapped
`linked_record_type` **denies**; it never falls through to allowed.

This tightens four routes the PF-1A-E1 baseline snapshot recorded as ungated
(`GET /api/documents/types`, `GET /api/documents/recent`,
`GET /api/documents/by-record/{record_type}/{record_public_id}`,
`POST /api/documents/metadata`). The frozen `BASELINE_UNGATED_ROUTES` fixture is left
byte-identical; the tightening is recorded additively in
`backend/tests/fixtures/post_baseline_tightened_routes.py`
(`POST_BASELINE_TIGHTENED_ROUTES`), consulted by the route-inventory guard test alongside the
frozen baseline. The frozen `ROLE_PERMISSION_COMPATIBILITY_MATRIX` (31 permissions / 110
grants) and `BASELINE_ROUTE_PERMISSION_INVENTORY` (76 routes) are unchanged.

### Events

`DocumentUploaded` on a successful upload (metadata only - never the file's bytes). The
existing `DocumentMetadataCreated` event on `POST /api/documents/metadata` is preserved, now
built through `record_business_event(...)`'s structured JSON encoding rather than hand-built
f-string interpolation, closing a JSON-injection defect where a `document_type` containing a
double quote could forge or corrupt the stored event payload.

### Deferred

Read-access auditing and retention policy are extended from the existing Slice 9D open
question in `docs/agent/DEFERRED_REQUIREMENTS.md` rather than answered separately - a document

### Slice 9E extension: system-generated documents

Slice 9E (Quotation Generation) adds a second document type - `QUOTATION`, joining
`DOCUMENT_TYPE_CODES` - and a second, internal-only storage entry point,
`store_generated_document()` in `documents/service.py`, used to store a document THIS
APPLICATION generates rather than one a user uploads.

`store_generated_document()` is **not reachable from any HTTP route**, by construction rather
than convention: it accepts content types only from `GENERATED_CONTENT_TYPES` (currently
`{"text/html": ".html"}` only), a closed map deliberately kept separate from
`ALLOWED_UPLOAD_EXTENSIONS`. `.html` is **not**, and must never become, an accepted upload
extension - letting a caller upload arbitrary HTML through `POST /api/documents/upload` would
put attacker-controlled markup into the store.

It shares one private helper (`_persist_stored_document`) with `upload_document()`, covering
storage-key generation, `provider.save`, the `document_metadata` insert and the
rollback-and-delete compensation on failure, so that compensation - a build-time correction in
Slice 9C - is reused rather than re-derived for a second call site. Unlike `upload_document()`,
it does **not** commit; the caller owns the transaction, because a generated document's row and
whatever record references it (a Commercial Offer quote-document version, for Slice 9E) must
land together or not at all.

### The compensation guarantee, and the gap the refactor briefly opened

`_persist_stored_document` compensates only for failures **inside itself**. Because it returns
before the caller commits, a failing `db.commit()` happens outside its reach: the transaction
rolls back and removes the `document_metadata` row, but the storage provider has already written
the object, which then survives with nothing referencing it - unreachable through the application
and invisible to any cleanup that works from rows.

Slice 9C held this guarantee by keeping `db.commit()` inside its own compensating try block.
Slice 9E's refactor moved the commit out and lost it for the commit-failure path specifically;
independent review reproduced the leak by fault injection (`delete_calls=0, rollback_calls=1`).
The guarantee is restored by `delete_stored_document_object(row)`, a shared best-effort helper
called by **both** `upload_document()` and Slice 9E's generation path after rollback. The rule for
any future caller of `_persist_stored_document`:

```text
If you commit after _persist_stored_document returns, you own the compensation for that commit
failing. Roll back AND call delete_stored_document_object(row).
```

A regression test fault-injects the failing commit and asserts on the **storage-object count**,
not merely on the database row - a rollback removes the row for free, so a row-only assertion
proves nothing about the bytes.

Its event is `DocumentGenerated`, a distinct name from `DocumentUploaded` - reusing the upload
event would record that a user uploaded a file they never uploaded, the same class of small lie
Slice 9C existed to remove. See `docs/agent/contracts/commercial-offer-contract.md` (Slice 9E
section) and `docs/agent/slices/slice-9e-quotation-generation.md` for the consuming feature.

## Record-scoped write rights (September 2026)

Owner decision, 11 September 2026: only people who can change a record may attach a file to it or
record document metadata against it. Until then, `POST /api/documents/upload` and
`POST /api/documents/metadata` were guarded only by `DOCUMENT_UPLOAD`, which every role holds, and
nothing checked the caller's rights on the linked record - or even that `linked_record_type` was a
known type.

Both routes now add a second, record-scoped, fail-closed check in the service layer, mirroring the
read side: the caller must hold the permission `DOCUMENT_LINK_WRITE_PERMISSION`
(`documents/contract.py`) names for the linked record type. Its keys are exactly those of
`DOCUMENT_LINK_READ_PERMISSION`, and a test pins that, so nothing can be attachable without also
being readable.

```text
linked_record_type          permission required                      roles today
account, business_party     ACCOUNT_DOCUMENT_CAPTURE                 Admin, Sales User, Sales Manager, Finance User
commercial_offer            COMMERCIAL_OFFER_PRICING_EVIDENCE_WRITE  Admin, Sales User, Sales Manager, Operations User
lead                        LEAD_UPDATE                              Admin, Sales User, Sales Manager
opportunity                 OPPORTUNITY_UPDATE                       Admin, Sales User, Sales Manager
work_order                  WORK_ORDER_CREATE                        Admin, Sales User, Sales Manager, Operations User
interaction                 INTERACTION_CREATE                       Admin, Sales User, Sales Manager
eligibility_certificate     EQUIPMENT_REFERENCE_MANAGE               Admin (the Fleet Admin, until that role exists)
anything else               refused, including a differently-cased or padded value
```

The owner decided the Account and Commercial Offer rows; the others apply the same rule - those who
can change the record - to the remaining linkable types. Account uses `ACCOUNT_DOCUMENT_CAPTURE`,
the grant `POST /api/accounts/{public_id}/documents` has carried since Slice 1J, so both ways of
attaching to an Account admit the same people. Management Read Only holds none of these and cannot
attach a file to anything.

Commercial Offer reuses `COMMERCIAL_OFFER_PRICING_EVIDENCE_WRITE`, which grants exactly the owner's
set - Operations holds it because Operations collects the market rates behind an offer - rather than
a dedicated permission. A dedicated code would need its own seed migration, because
`has_permission()` reads the seeded `authz_role_permission` table, and the next migration slot is
reserved for the Hiring lane. The cost is coupling: changing who may record pricing evidence also
changes who may attach files to an offer. Splitting them later takes one post-baseline code, its
seed migration and a change to this map entry.

`DOCUMENT_UPLOAD` itself is unchanged: all six roles hold it, and it only admits a caller to the two
routes; as with `DOCUMENT_READ`, the real narrowing is the record-scoped check. The permission
catalogue's descriptions of `DOCUMENT_UPLOAD` and `COMMERCIAL_OFFER_PRICING_EVIDENCE_WRITE` predate
this decision and are unchanged, so they understate what those grants now govern.

Order of checks, for both routes: the request body is capped as it arrives (`413`, before
authentication; see "Upload limits" above). Then every check on the request itself - the form
fields, the reserved `QUOTATION` type and, for an upload, the file's extension and declared content
type - then the rights check (`403`), then, for an upload, the content check (`422`) and the size
limit while the file streams into the store (`413`). A malformed request is therefore a `422`
whoever sends it. A refused request stores nothing in the document store, writes no row and records
no event, and the service never reads a refused upload's file, because the content check runs
after the rights check. The web framework has already received the request body by then, as it does
for every form - which is why the cap exists. On the metadata route a whitespace-only
`linked_record_type` is now refused with `422`, as the upload route already did; it used to create
a row.

`upload_document()` and `create_document_metadata()` perform no authorization. They are the trusted
entry points for in-process callers such as the smoke-data harness and tests; the HTTP routes call
`upload_document_for_caller()` and `create_document_metadata_for_caller()`, which carry the check.

### QUOTATION is refused from users

`DOCUMENT_TYPE_CODES` includes `QUOTATION` for system-generated quotations (Slice 9E), and until
September 2026 both user paths accepted it as well, so a user could upload a file that listed as a
generated quotation. `SYSTEM_GENERATED_DOCUMENT_TYPE_CODES` now names the types only the
application may set. An upload accepts only `UPLOADABLE_DOCUMENT_TYPE_CODES` - every type except
`QUOTATION`. The metadata route still accepts free-text types, as it always has, but refuses
`QUOTATION` in any capitalisation or spacing. Both refusals are `422`, and the trusted functions
refuse it too. `store_generated_document()` is unchanged and still stores generated quotations.

### Where users attach files

Files are listed, downloaded and uploaded on the Account page and on the Commercial Offer page,
through one shared component, `frontend/src/components/DocumentsPanel.tsx`. The upload form is shown
only to the roles above for that record type; that is a usability aid, and the server enforces the
rule. The browser declares each file with the content type the server expects for its extension,
because browsers report some types inconsistently (Windows often reports `.csv` as
`application/vnd.ms-excel`); the server still checks that the declared type matches the extension,
and that the file's content matches its format.

If the connection fails, or the server answers with an error of 500 or above, the form says the
upload could not be confirmed and reloads the list, because the file may have been stored before the
failure. Uploads carry no idempotency key: storing one needs a schema change, and the next migration
slot is reserved for the Hiring lane.

The Documents page lists recent documents with downloads; its developer test tools, including the
upload box that always filed to one fixed sample Account, are removed.

See `docs/agent/slices/document-upload-on-record-pages.md`.

## A machine certificate's copy (ELG-1, 27 September 2026)

ELG-1 attaches the copy of each machine certificate - registration, insurance, pollution certificate, road
tax, fitness, permit, thorough examination or load test - as a document linked to the certificate
(`docs/agent/contracts/eligibility-api-contract.md`). Code only: `linked_record_type` is free text, so no
table changes.

- **Linked record type `eligibility_certificate`**, in both maps of `documents/contract.py`: reading and
  downloading need `EQUIPMENT_IDENTITY_READ` - a copy shows the certificate's number, and often the engine
  and chassis numbers, which only Admin may see (owner, 25 and 27 September 2026, Q6); attaching needs
  `EQUIPMENT_REFERENCE_MANAGE`, as recording the certificate does.
- **Document type `CERTIFICATE`**, one of the types a user may choose (`UPLOADABLE_DOCUMENT_TYPE_CODES`).
  The machine page's panel offers only it.
- **The owning module's check on one record.** `DOCUMENT_LINK_TYPES_WITH_ATTACH_CHECK` names the types whose
  owning module decides whether a file may be attached to one particular record; the module registers its
  check with `register_attach_check` when it is imported, so the documents module does not import it.
  It is told the document type and storage mode. Eligibility's refuses (`422`) any type but `CERTIFICATE`, a link to
  a file kept elsewhere, and a copy for a withdrawn or unknown certificate; it takes Eligibility's write lock,
  held until the document's transaction ends, so a withdrawal cannot slip between the check and the copy being
  stored. It runs on both write paths -
  `upload_document()` and `create_document_metadata()`, and so behind both routes - after the rights check
  and before the file is read. Fail-closed: a listed type with no registered check refuses every attachment.
- **Whether a certificate has a copy** is read by Eligibility through `linked_record_ids_with_documents()`, a
  trusted function that reads no rights and says only whether a file of a given type and storage mode exists,
  not rejected or archived: everyone who sees a certificate may know whether its copy is attached, while the
  copy itself stays behind `EQUIPMENT_IDENTITY_READ`.
- On the machine page the shared `DocumentsPanel` shows a certificate's copies, and its form, to Admin; it
  gained two optional props for this - `documentTypes` (the types offered; with one, it is chosen) and
  `onUploaded` (so the page shows the certificate counting once its copy is attached).

## A market rate's quote copy (Slice 4G, 11 October 2026)

A broker's quote behind a Commercial Offer market rate - a WhatsApp screenshot, an email kept as a PDF or picture, a
PDF or Word document - is attached to the rate (`commercial-offer-contract.md`, "Slice 4G"). Code only: no table
changes.

- **Linked record type `commercial_offer_market_rate`**, in both maps of `documents/contract.py`: reading and
  downloading need `COMMERCIAL_OFFER_READ`, as reading the offer's rates does; attaching needs
  `COMMERCIAL_OFFER_PRICING_EVIDENCE_WRITE`, as recording them does.
- **Document type `VENDOR_QUOTE`**, offered on the rate's panel only. `DOCUMENT_TYPE_ONLY_FOR_LINK_TYPE` keeps it to
  `commercial_offer_market_rate`: both routes refuse (`422`) it against any other linked record type, before the rights
  check, so a quote cannot be filed where the rate's own check does not run.
- **The owning module's check** (`register_attach_check`, as ELG-1's): Commercial Offers refuses any type but
  `VENDOR_QUOTE`, a link to a file kept elsewhere, a rate recorded for the whole offer, a rate on a cancelled line and a
  rate on a version that can no longer change; it takes the offer's lock, held until the document's transaction ends.
- **Reading a rate's quotes.** Commercial Offers reads them through `documents_linked_to_records()`, a trusted function
  that reads no rights and returns each document's id, file name and time; the rate's response carries them only to
  callers who may read the rate, and downloading checks the link's read right again.
